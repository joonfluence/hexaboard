## 범위

**포함**: 티켓 생성, 공개 식별자로 티켓 한 건 조회, 잘못된 요청에 대한 오류 응답. 서버(백엔드)만 다룬다.

**제외**: 목록 조회, 수정, 삭제, 카드 이동, 정렬, 태그, 필터, 프론트엔드. 이후 기능에서 다룬다.

## Clarifications

### Session 2026-09-21

- Q: 제목 앞뒤 공백은 어떻게 저장하는가? → A: 앞뒤 공백을 제거해 저장한다. 길이 100자 검사도 제거 후 기준이다.
- Q: 설명을 빈 문자열이나 공백뿐으로 보내면? → A: "설명 없음"(`null`)으로 저장한다. 생략·`null`·빈 문자열·공백뿐이 모두 같은 상태다.
- Q: 범위 밖 필드(예: `tags`)가 생성 요청에 있으면? → A: `tags`만 `400`으로 거부하고, 이름이 전혀 다른 미지 필드는 무시한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새 티켓 만들기 (Priority: P1)

개발자(본인)가 제목을 입력해 새 티켓을 만든다. 티켓은 항상 `TODO` 상태로 시작하고, 우선순위를 주지 않으면 기본값(`MEDIUM`)이 적용된다. 생성 결과로 티켓의 공개 식별자를 받는다. ([US-01](../../docs/user_stories.md))

**Why this priority**: 티켓이 없으면 나머지 모든 기능(조회, 이동, 정렬 등)이 성립하지 않는다. 앱의 가장 기본 가치다.

**Independent Test**: 제목만 담아 생성을 요청하고, 응답이 상태 `TODO`, 우선순위 `MEDIUM`, 새 공개 식별자를 담고 있는지 확인한다. 이것만으로 "기록할 수 있다"는 가치가 전달된다.

**Acceptance Scenarios**:

1. **Given** 유효한 제목만 있는 요청, **When** 티켓을 생성하면, **Then** 성공 응답과 함께 상태 `TODO`, 우선순위 `MEDIUM`, 새 공개 식별자를 가진 티켓이 돌아온다.
2. **Given** 제목, 설명, 우선순위(`HIGH`), 마감일을 담은 요청, **When** 티켓을 생성하면, **Then** 입력한 값이 그대로 저장되어 응답에 담긴다.
3. **Given** 우선순위를 생략한 요청, **When** 티켓을 생성하면, **Then** 우선순위는 `MEDIUM`이다. (우선순위를 `null`로 비우는 요청은 거부된다.)
4. **Given** 같은 내용의 생성 요청을 두 번 보내면, **When** 각각 처리되면, **Then** 서로 다른 공개 식별자를 가진 별개의 티켓 두 개가 만들어진다.
5. **Given** 같은 컬럼에 동시에 생성 요청이 들어와 순서가 충돌할 때, **When** 재시도 안에 해소되면, **Then** 정상 생성으로 응답하고, 재시도 후에도 충돌하면 `409` 충돌 오류를 돌려주며 티켓은 만들어지지 않는다.

---

### User Story 2 - 티켓 한 건 조회하기 (Priority: P1)

개발자(본인)가 공개 식별자로 티켓 한 건을 조회해 저장된 내용을 확인한다. ([US-02](../../docs/user_stories.md)의 조회 부분)

**Why this priority**: 생성이 제대로 저장됐는지 확인하는 유일한 수단이며, 생성과 함께 있어야 슬라이스가 독립적으로 검증된다.

**Independent Test**: 티켓을 하나 만들고, 응답의 공개 식별자로 조회해 생성 시 입력한 값이 그대로 돌아오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이미 만들어진 티켓, **When** 그 공개 식별자로 조회하면, **Then** 생성 시 저장된 제목·설명·상태·우선순위·마감일이 돌아온다.
2. **Given** 존재하지 않는 공개 식별자(형식은 올바름), **When** 조회하면, **Then** "티켓 없음" 오류가 돌아온다.
3. **Given** 공개 식별자 형식이 아닌 값, **When** 조회하면, **Then** "식별자 형식 오류"가 돌아온다.
4. **Given** 어떤 응답이든, **When** 내용을 살펴보면, **Then** DB 내부 식별자는 어디에도 포함되어 있지 않다.

---

### User Story 3 - 잘못된 생성 요청 거부하기 (Priority: P2)

개발자(본인)가 잘못된 값으로 생성을 요청하면, 무엇이 왜 틀렸는지 알 수 있는 오류를 받고 티켓은 만들어지지 않는다.

**Why this priority**: 기본 흐름이 아니라 방어이므로 P1 뒤에 온다. 하지만 도메인 규칙(제목 검증)이 이 슬라이스에서 처음 구현되므로 함께 다룬다.

**Independent Test**: 각 검증 규칙을 위반하는 요청을 하나씩 보내 모두 오류 응답을 받고, 이후에도 잘못된 티켓이 저장되지 않았는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 제목이 없거나 `null`, 빈 문자열, 공백뿐인 요청, **When** 생성하면, **Then** 검증 실패 오류가 돌아오고 티켓은 만들어지지 않는다.
2. **Given** 제목이 100자 초과 또는 설명이 2000자 초과인 요청, **When** 생성하면, **Then** 검증 실패 오류가 돌아온다.
3. **Given** 우선순위가 허용 값(`LOW`/`MEDIUM`/`HIGH`/`URGENT`)이 아닌 요청, **When** 생성하면, **Then** 검증 실패 오류가 돌아온다.
4. **Given** 마감일이 시각 형식(ISO 8601)이 아닌 요청, **When** 생성하면, **Then** 검증 실패 오류가 돌아온다.
5. **Given** 서버가 정하는 값(공개 식별자, 상태, 순서, 생성·수정 시각)을 본문에 담은 요청, **When** 생성하면, **Then** 무시하지 않고 거부한다.
6. **Given** `tags`를 담은 요청, **When** 생성하면, **Then** 거부된다. 이름이 전혀 다른 미지 필드만 더한 요청은 그 필드를 무시하고 생성된다.
7. **Given** 본문이 올바른 JSON이 아니거나 JSON이 아닌 형식의 요청, **When** 생성하면, **Then** 각각 정해진 오류가 돌아온다.

---

### Edge Cases

- 제목이 정확히 100자, 설명이 정확히 2000자인 경계값은 허용된다. 각각 1자 초과하면 거부된다.
- 제목 앞뒤 공백은 제거해 저장하며, 제거 후 길이로 100자를 검사한다. 앞뒤 공백 때문에 100자를 넘긴 제목도 제거 후 100자 이하면 허용된다.
- 설명이 생략·`null`·빈 문자열·공백뿐이면 "설명 없음"으로 저장된다.
- 마감일이 생략되면 "마감일 없음"으로 저장된다.
- 태그는 이 슬라이스의 범위 밖이다. 생성 요청에 `tags`를 담으면 `400`으로 거부한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 제목(필수)과 설명·우선순위·마감일(선택)로 티켓을 생성할 수 있어야 한다. 설명이 생략·`null`·빈 문자열·공백뿐이면 "설명 없음"(`null`)으로 저장한다. ([FR-01](../../docs/functional_requirements.md))
- **FR-002**: 생성된 티켓의 상태는 항상 `TODO`여야 한다. 요청으로 상태를 지정할 수 없다. ([FR-02](../../docs/functional_requirements.md))
- **FR-003**: 우선순위를 생략하면 `MEDIUM`을 적용해야 하며, `null`로 비우는 요청은 거부해야 한다. ([FR-06](../../docs/functional_requirements.md))
- **FR-004**: 제목은 앞뒤 공백을 제거한 뒤 비어 있지 않아야 하고(공백뿐인 경우 포함) 최대 100자, 설명은 최대 2000자여야 한다. 위반하면 검증 실패로 거부해야 한다. 제목은 앞뒤 공백을 제거한 값으로 저장한다.
- **FR-005**: 티켓마다 서버가 새 공개 식별자(`ticketId`, UUID v4)를 만들어야 하며, 이 값은 DB 내부 식별자와 별개다. 내부 식별자는 어떤 응답에도 노출하지 않아야 한다. ([데이터 모델](../../docs/data_model.md))
- **FR-006**: 서버가 정하는 값(`ticketId`, `status`, `position`, `createdAt`, `updatedAt`)이 생성 요청 본문에 있으면 무시하지 않고 거부해야 한다. 이 기능 범위 밖의 `tags`도 `400`으로 거부하고, 이름이 전혀 다른 미지 필드는 무시한다. ([API 명세](../../docs/api_spec.md))
- **FR-007**: 공개 식별자로 티켓 한 건을 조회할 수 있어야 하며, 없으면 "티켓 없음"(`TICKET_NOT_FOUND`), 형식이 잘못되면 `INVALID_TICKET_ID` 오류를 돌려줘야 한다.
- **FR-008**: 모든 오류 응답은 [API 명세의 오류 응답 형식](../../docs/api_spec.md)(`statusCode`, `code`, `message`, 검증 실패 시 `details`)을 따라야 한다. 검증 실패는 `400`으로 통일한다.
- **FR-009**: 새로 만든 티켓은 `TODO` 컬럼의 맨 뒤(기존 카드들 다음)에 놓여야 한다. 기존 카드의 순서는 바뀌지 않는다. ([결정 D-79](../../docs/decision_log.md))
- **FR-013**: 같은 컬럼에 동시에 생성되어 순서가 충돌하면 서버가 다시 계산해 재시도(최초 시도 후 최대 3회)하고, 재시도로 성공하면 정상 생성으로 응답한다. 재시도 후에도 실패하면 충돌 오류(`409`, `POSITION_CONFLICT`)를 돌려주고 티켓은 만들어지지 않는다. ([결정 D-84](../../docs/decision_log.md), [API 명세](../../docs/api_spec.md))
- **FR-010**: 티켓 응답에는 순서 값(`position`)을 포함하지 않아야 한다. 순서는 목록 조회의 정렬 결과로만 드러난다. ([결정 D-80](../../docs/decision_log.md))
- **FR-011 (개발 방식)**: 이 기능은 **TDD로 개발해야 한다.** 모든 프로덕션 코드는 실패하는 테스트를 먼저 작성해 실패(Red)를 확인한 뒤 구현(Green)하고, 통과 후 정리(Refactor)한다. 작업 목록에는 구현 태스크보다 앞선 테스트 태스크, Red 확인, Refactor가 모두 포함되어야 한다. ([헌법 원칙 III](../../.specify/memory/constitution.md))
- **FR-012 (구조)**: 이 기능은 [계층 경계 규칙](../../docs/trd/04-layer-boundaries.md)을 지켜야 한다. 제목 검증 같은 도메인 규칙은 프레임워크를 모르는 도메인 계층에, 요청 형식 검증과 오류 코드 변환은 웹 계층에만 둔다.

### Key Entities *(include if feature involves data)*

- **티켓(Ticket)**: 사용자가 관리하는 일 한 건. 공개 식별자, 제목, 설명(선택), 상태, 우선순위, 마감일(선택), 컬럼 안 순서, 생성·수정 시각을 가진다. 태그는 이 슬라이스에서 다루지 않는다.
- **제목(Title)**: 비어 있지 않고 100자 이하여야 하는 값. 검증 규칙을 스스로 가진다.
- **우선순위(Priority)**: `LOW` / `MEDIUM` / `HIGH` / `URGENT` 네 단계 중 하나. 생략 시 `MEDIUM`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 유효한 생성 요청의 100%가 새 공개 식별자와 상태 `TODO`를 가진 티켓을 만들고, 그 식별자로 즉시 조회하면 생성 시 입력한 값이 100% 일치해서 돌아온다.
- **SC-002**: 명세에 열거한 검증 위반 유형(제목 누락·빈 값·공백·100자 초과, 설명 2000자 초과, 잘못된 우선순위·마감일 형식, 서버 지정 값 포함, 잘못된 본문, 재시도 후에도 지속되는 순서 충돌)마다 오류 응답이 나오고, 위반 요청으로 저장된 티켓은 0건이다.
- **SC-003**: 어떤 응답에서도 DB 내부 식별자가 발견되지 않는다 (검사 대상 응답의 100%).
- **SC-004**: 이 기능의 모든 새 동작은 구현 전에 작성된 테스트로 검증되며, 각 테스트는 구현 전 실패(Red)가 확인된 이력을 가진다.
- **SC-005**: 계층 경계 위반(도메인이 프레임워크를 참조하는 등)이 0건이다.

## Assumptions

- 사용자는 개발자 본인 한 명이며 인증은 없다. ([NFR-04](../../docs/non_functional_requirements.md))
- 대상은 백엔드 API다. API 경로는 `/v1/tickets`이고 `POST /tickets`, `GET /tickets/{ticketId}`가 이 기능의 엔드포인트다. ([API 명세](../../docs/api_spec.md))
- 마감일은 이 슬라이스에 선택 입력으로 포함한다 (생성 입력 목록에 있고 구현 비용이 작다). 표시 방식은 프론트의 미결 항목이라 이 기능과 무관하다.
- 응답에는 태그 필드를 두지 않는다. `tags` 거부는 이 슬라이스에 한정된 임시 규칙이며 태그 기능을 다룰 때 폐기한다.
- 응답 필드 이름은 camelCase, 시각은 UTC ISO 8601이다. ([API 명세 표현 예시](../../docs/api_spec.md))
- 정확한 요청·응답 스키마 상세는 구현 시 OpenAPI로 확정한다. ([open_questions.md](../../docs/open_questions.md))
- 저장 방식과 스키마 관리는 [데이터 모델](../../docs/data_model.md)을 따른다. 이 기능은 티켓 저장을 처음 도입하므로 첫 스키마 마이그레이션을 포함한다.
