# 데이터 모델

티켓(`ticket`)을 중심으로 한 데이터 모델이다. 확정된 필드만 적고 정해지지 않은 것은 "미정"으로 표시한다. 도메인 모델과 영속성 엔티티는 별개 클래스이며 매퍼가 변환한다. ([TRD 계층 간 경계 규칙](trd/04-layer-boundaries.md))

## 관계

```
ticket ──N:M── tag      (연결 테이블 ticket_tag)
```

## ticket

| 필드 | 타입 | 필수 | 규칙 |
|------|------|------|------|
| `id` | `bigint` 자동 증가 | 필수 | **내부 PK**. DB 안에서만 쓰고 API와 도메인 모델에 노출하지 않는다 |
| `public_id` | UUID | 필수 | **공개 식별자**(별도 유니크 키). 도메인(`Ticket.create()`)에서 생성. UUID v4(무작위). API의 `ticketId`에 대응(매퍼가 변환) |
| `title` | 문자열 | 필수 | 도메인의 Title 값 객체가 검증. 최대 100자 (DB 컬럼 길이도 100) |
| `description` | text | 선택 | 최대 2000자 (도메인·DTO에서 검증) |
| `status` | `text` + CHECK 제약 | 필수 | `TODO` / `IN_PROGRESS` / `DONE`. 생성 시 항상 `TODO`. 전이는 자유 |
| `priority` | `smallint` | 필수 | 도메인·API는 `LOW` / `MEDIUM` / `HIGH` / `URGENT`. 기본값 `MEDIUM` |
| `due_at` | `timestamptz` | 선택 | 날짜+시간. UTC 저장, 표시 시 변환 |
| `position` | `text COLLATE "C"` | 필수 | 컬럼(상태) 안 카드 순서. 사전순으로 정렬되는 키. (상태, `position`)은 유니크 |
| `created_at` | `timestamptz` | 필수 | 생성 시각. ORM 훅이 채움 |
| `updated_at` | `timestamptz` | 필수 | 수정 시각. ORM 훅이 채움 |

`status`는 문자열 컬럼에 CHECK 제약으로 저장한다. DB enum 타입은 값 변경 시 마이그레이션 부담이 커서 쓰지 않는다.

## 식별자 (PK와 `ticketId` 분리)

- 외부에 노출하는 식별자 `ticketId`는 DB PK가 아니라 **별도 유니크 키**다. 보안을 위한 결정이다. 순차적일 수 있는 내부 PK가 API에 드러나면 다른 티켓의 id를 추측할 수 있기 때문이다.
- 내부 PK(`id`)는 영속성 엔티티에만 존재한다. 도메인 모델은 `ticketId`만 갖고, 매퍼가 둘을 대응시킨다.
- 도메인이 저장 전에도 완전한 객체여야 하므로 `ticketId`는 도메인에서 생성한다. DB PK는 저장 시점에 DB가 정해도 무방하다.
- 조회·수정·삭제는 `ticketId`로 찾는다. 다른 테이블의 외래 키(`ticket_tag` 등)는 내부 PK를 참조하는 것을 초안으로 한다.
- UUID v4를 쓴다. 생성 시각이 드러나는 v7은 별도 키로 분리한 보안 목적과 맞지 않아 채택하지 않았다.
- 내부 PK는 `bigint` 자동 증가이고 컬럼명은 `id`다. 공개 식별자 컬럼명은 `public_id`로, 다른 테이블의 외래 키 `ticket_id`(예: `ticket_tag.ticket_id`)와 헷갈리지 않게 했다.

## tag / ticket_tag

- `tag`: 자유 입력 태그. 내부 PK `id`(`bigint` 자동 증가)와 이름 `name`(최대 30자)을 가진다. 이름에 유니크 제약을 건다. 공개 식별자는 두지 않는다.
- `ticket_tag`: 티켓과 태그를 잇는 연결 테이블. 두 테이블의 내부 PK를 참조한다 (`ticket_id`, `tag_id`).
- 정규화: 태그 이름은 앞뒤 공백을 제거하고 소문자로 바꿔 저장한다. `Docs`와 `docs`는 같은 태그다.
- 티켓당 태그는 최대 10개다. 초과하면 요청을 거부한다 (`400`).
- 이 규칙들은 도메인 불변식으로는 채택하지 않았다.

## 우선순위 변환

- DB에는 순서를 나타내는 숫자로 저장한다: `LOW`=1, `MEDIUM`=2, `HIGH`=3, `URGENT`=4 (매퍼 테스트로 고정).
- 이렇게 하면 DB에서 정렬이 자연스럽다. 문자열로 저장하면 알파벳순(`HIGH` → `LOW` → `MEDIUM`)이 되기 때문이다.
- 순서 지식은 도메인의 `Priority` 값 객체와 매퍼에만 둔다.

## position (순서 키)

- 문자열 순서 키다 (LexoRank·fractional indexing 계열). 카드 하나를 옮길 때 그 카드 한 건만 갱신한다.
- 계산은 도메인의 `Position` 값 객체가 맡는다. 두 이웃 카드의 키 사이의 새 키를 만든다. 이웃 카드는 `application`이 포트로 조회해 넘긴다.
- 라이브러리 없이 직접 구현하며 경계 조건 테스트가 필수다.
- 키는 바이트 순서로 비교되어야 하므로 컬럼에 바이너리 정렬(`C` collation)이 필요하다. 스키마에서 `position` 컬럼에만 `COLLATE "C"`를 명시하고 마이그레이션에 반영한다. DB 전체 collation에 의존하지 않아 로컬·Neon·테스트 컨테이너에서 동일하게 동작한다.
- 키는 같은 상태 컬럼 안에서만 비교한다. 다른 컬럼으로 옮기면 대상 컬럼의 이웃 카드를 기준으로 새 키를 계산한다.
- (상태, 순서 키)에 유니크 제약을 건다. 동시 이동으로 충돌하면 서버가 이웃 카드를 다시 읽어 키를 재계산해 재시도하고, 계속 실패하면 `409`로 응답한다.
- 재시도는 최초 시도 후 최대 3번이다. 값은 상수 하나로 둔다.
- 별도 재정규화 로직은 두지 않는다. 정렬(`POST /tickets/sort`)이 순서를 새로 쓰므로 그때 키가 짧아진다.
- 미정: 순서 키 길이 상한과 넘을 때의 처리 (구현 시 확정)

## 시각 필드

- `created_at`, `updated_at` 둘 다 둔다.
- `persistence`의 MikroORM 훅이 생성·수정 시 채운다. 도메인은 시계를 모른다.

## 마이그레이션

- 마이그레이션 파일은 `persistence`에 두고, CLI 설정과 실행 스크립트는 `bootstrap-http`에 둔다.
- 서버 기동 시 자동 실행한다. 실패하면 기동을 중단하고 복구는 수동이다. ([TRD 배포 전략](trd/06-deployment.md))
