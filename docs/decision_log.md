# 결정 로그

확정된 결정과 근거다. 정해지지 않은 항목은 [open_questions.md](open_questions.md)를 본다. 이 문서는 소크라틱 대화로 정한 순서대로 정리했다.

## 목적·범위

| # | 결정 | 근거 |
|---|------|------|
| D-01 | 학습용 풀스택 웹 앱 | 기술 연습이 목적. 기능의 참신함은 우선순위가 아님 |
| D-02 | 데이터는 백엔드 서버 + DB에 저장 | 풀스택(프론트+백엔드+DB) 학습 |
| D-03 | MVP에서 인증 제외, 단일 사용자 | MVP 범위를 좁게 유지. 인증은 2차 |
| D-04 | 완료 기준: 기능 체크리스트 100% + 배포 | 실제 URL로 접근 가능한 결과물이 학습 목표 |
| D-05 | 구조 연습 필수 3개(백엔드 구조, API 계약 공유, 마이그레이션), 테스트+CI/CD는 best-effort | 나중에 붙이기 어려운 것을 필수로, 붙이기 쉬운 것은 best-effort |

## 기술 스택

| # | 결정 | 근거 |
|---|------|------|
| D-06 | TypeScript로 FE/BE 통일 | 생산성 극대화 |
| D-07 | Next.js와 NestJS를 분리 | 엔터프라이즈 수준 구조 학습. 서버가 둘이 되는 복잡도는 학습 비용으로 수용 |
| D-08 | Next.js는 클라이언트 중심, SSR 최소화 | SSR 자체는 불필요(선택 배경은 Vercel 배포). 서버 모델은 인증 도입 시 2차로 학습 |
| D-09 | TanStack Query + openapi-fetch | 스펙에서 타입만 생성하고 호출·캐시는 직접 구성해 생성물이 적음 |
| D-10 | API 계약: Nest DTO + swagger로 OpenAPI 생성, 수동 명령 + 생성물 커밋 | 서버가 진실 원천, Nest 관례에 부합. 수동 방식은 단순함 우선 |
| D-11 | ORM은 MikroORM | 가장 많이 써봐서 생산성이 높고 엔터프라이즈 패턴과 부합 |
| D-12 | DB는 Neon(Postgres), 잠정 | 무료 우선. 요금·유휴 정책 재확인 필요 |
| D-13 | 웹 Vercel, 서버 Render 무료 플랜(잠정), 유휴 지연 허용 | 무료 플랫폼 우선. Nest는 상시 서버라 서버리스 Vercel과 부적합 |
| D-14 | 모노레포, pnpm + Turborepo | 한 명이 풀스택으로 개발. 레포를 분리할 이유가 없음 |
| D-15 | 백엔드 헥사고날, weave-server 참고 | 엔터프라이즈 구조 학습 |
| D-16 | 계층 경계를 패키지 단위로 강제 | 위반이 빌드 단계에서 드러남 (폴더 단위 + lint 대신) |
| D-17 | `domain`만 프레임워크 프리, `application`은 Nest 데코레이터 허용 | 생산성 우선. weave-server와 같은 실용적 타협 |
| D-18 | 포트는 `interface` + Symbol 토큰, Inbound/Outbound 통일 | TS `interface`는 런타임에 없어 토큰이 필요. 포트를 순수 계약으로 유지 |
| D-19 | 도메인 모델과 영속성 엔티티 분리, 별도 엔티티 + 매퍼 | 헥사고날 어댑터 개념이 드러나고 도메인이 ORM을 모름 |
| D-20 | API 클라이언트는 별도 패키지 `api-client` | 모노레포에서 계약이 눈에 보이게 |
| D-21 | 패키지 구성: `web`, `bootstrap-http`, `domain`, `application`, `persistence`, `api-client` | `api`는 HTTP만 가리키는 좁은 이름이라 `bootstrap-http`로. 공통 패키지는 필요할 때 추가 |
| D-22 | 마이그레이션 파일은 `persistence`, CLI 설정·실행은 `bootstrap-http` | `persistence`가 `bootstrap-http`를 import하면 순환 의존이므로 금지 |
| D-23 | FSD 채택, Next `app`은 라우팅 껍데기, FSD `pages`는 `views`로 개명 | 우회용 빈 `pages/` 폴더 없이 충돌을 피함 |
| D-24 | 테스트 도구: 백엔드 Jest, 프론트 Vitest | 각 진영 기본값을 따르는 안정성 (데코레이터 메타데이터 이슈 회피) |
| D-25 | 백엔드 테스트 범위: domain 단위, persistence 통합, API/컨트롤러. `application` 단위 테스트는 2차 | API 테스트가 전체 경로를 검증하므로 Fake 포트가 필요 없음 |
| D-26 | 테스트용 DB는 Testcontainers | 로컬/CI 동일 방식과 격리. Docker 필요 |
| D-27 | CI는 GitHub Actions, 저장소는 GitHub 공개. 비밀값은 커밋하지 않음 | 저장소·배포 연동이 한곳. 공개 저장소라 시크릿 관리가 중요 |
| D-28 | 배포는 단일 환경, `main`만 배포, `development`는 CI 검증용 | 무료 한도 안에서 단순하게 |
| D-29 | 마이그레이션은 서버 기동 시 자동 실행 | 배포와 항상 함께 움직임. Render pre-deploy 기능에 의존하지 않음 |
| D-30 | 스타일링은 Tailwind CSS + shadcn/ui | 생산성이 높고 Next 생태계에서 흔함 |
| D-31 | 드래그 앤 드롭은 dnd-kit | 범용 툴킷. 보드 로직을 직접 조립 |

| D-32 | 도메인 용어는 "티켓"(테이블 `ticket`) | 할 일의 새 이름. 범위 변화 없음 |
| D-33 | 상태 enum `TODO`/`IN_PROGRESS`/`DONE`, 전이는 자유 | 프론트 상태 UI 연습. 도메인 불변식은 제목 검증(Title 값 객체)만 채택 |

| D-35 | 태그는 자유 입력 + `tag` 테이블(N:M), 카테고리 제외 | N:M 매핑 연습, 카테고리 관리 CRUD로 범위가 커지는 것을 피함 |

| D-38 | `created_at`, `updated_at` 둘 다 도입 | 최신순 정렬과 디버깅에 유용 |
| D-39 | UI는 상태별 보드형, Trello 참조 | 프론트 상태 UI(드래그, 낙관적 업데이트) 연습 |

## 점검 후 추가된 결정

| # | 결정 | 근거 |
|---|------|------|
| D-43 | 인증 없는 공개 배포의 위험을 수용하고, 인증은 향후 고도화에서 추가 | MVP 범위를 좁게 유지. URL을 아는 누구나 접근·수정 가능한 위험을 인지한 상태로 결정 |
| D-44 | 로컬 개발용 DB는 로컬 PostgreSQL | 배포 DB(Neon)와 같은 Postgres 계열이라 동작 차이가 작음. 실행 방식은 미정 |
| D-45 | API는 RESTful하게 `tickets` 리소스로 정의. 카드 이동은 `PUT /tickets/{ticketId}/position`, 정렬은 `POST /tickets/sort`로 확정 | 복수 명사 리소스, URI에 동사 금지. 이동은 위치를 설정하는 멱등 하위 리소스이고 `PATCH`와 이동 규칙이 분리됨. 정렬은 컬렉션 전체에 대한 명령이라 동사 URI 한 곳만 예외로 둠 |
| D-46 | `ticketId`는 DB PK가 아니라 별도 유니크 키(공개 식별자)로 처리. 내부 PK는 API·도메인에 노출하지 않음 | 보안: 순차적일 수 있는 내부 PK가 외부에 드러나 다른 티켓 id를 추측하는 것을 막음. 내부 PK 타입은 D-50에서 `bigint` 자동 증가로 결정 |
| D-47 | `ticketId`의 UUID 버전은 v4 (D-37의 v7에서 변경) | 별도 키로 분리한 보안 목적과 일관되게 생성 시각을 노출하지 않음. PK가 분리되어 v7의 인덱스 지역성 이점이 사라졌고, 이 규모에서 v4의 흩어짐 비용은 무시할 수준 |
| D-48 | 순서 키는 같은 상태 컬럼 안에서만 비교, 컬럼 간 이동 시 대상 컬럼의 이웃 카드가 기준 | 기준 카드 앞/뒤 방식의 필연적 결과 |
| D-49 | 동시 이동 충돌은 (상태, 순서 키) 유니크 제약 + 서버 재시도, 계속 실패하면 `409` | 실서비스에 가까운 동시성 처리를 연습. 데이터가 항상 깨끗함. 재시도·`409` 처리 비용은 수용 |
| D-50 | 내부 PK는 `bigint` 자동 증가, `status`는 문자열 + CHECK, `created_at`/`updated_at`은 ORM 훅이 채움, `position` 컬럼에만 `COLLATE "C"` 지정 | 내부 전용 PK는 단순하고 작게. 값 변경 시 마이그레이션이 가벼움. 도메인이 시계를 모르게 유지. DB 설정에 의존하지 않아 로컬·Neon·테스트에서 동일하게 동작 |
| D-51 | 제목 최대 100자, 설명 최대 2000자. 생성 시 우선순위를 생략하면 `MEDIUM` 적용. 서버가 정하는 값을 본문에 보내면 `400`으로 거부 | 카드 제목·메모 용도에 충분한 길이. 생략은 관대하게(도메인 기본값이 이미 `MEDIUM`), 금지 필드는 엄격하게 거부해 클라이언트 버그를 빨리 드러냄 |
| D-52 | API 오류 설계 확정: 검증 실패는 `400` 통일, 응답은 `statusCode`/`code`/`message`/`details[]`, 오류 코드는 `VALIDATION_FAILED` 등 (api_spec.md 예외 섹션) | 프론트가 문구가 아니라 `code`로 분기. 형식·타입 검증(DTO)과 도메인 규칙(값 객체)을 모두 `400`으로 응답 |
| D-53 | 컬럼명: 내부 PK는 `id`, 공개 식별자는 `public_id` | 외래 키를 `ticket_id`로 쓸 때 공개 식별자 컬럼과 헷갈리지 않게 함. API 필드 `ticketId`와의 대응은 매퍼가 맡음 |
| D-54 | 태그: 이름은 앞뒤 공백 제거 + 소문자 정규화, 이름 유니크, 이름 최대 30자, 티켓당 최대 10개, `tag`는 내부 `id`(bigint)만 가짐. 도메인 불변식으로는 채택하지 않음 | `Docs`/`docs` 중복 태그가 쌓여 필터가 무의미해지는 것을 방지. 개수·길이 제한은 비정상적으로 큰 요청을 막는 저렴한 방어 |
| D-55 | 정렬: 컬럼 단위, 기준은 우선순위·마감일(방향은 실행 시 지정), 마감일 없는 티켓은 항상 맨 뒤, 실행 취소 없음 | 카드 이동의 순서 범위와 일치. 마감일 없는 티켓은 급하지 않으므로 뒤에 둠. undo는 이전 순서 저장으로 범위가 커져 MVP에서 제외. 생성일 기준은 제공하지 않음 |
| D-56 | 보드 UI는 Trello 조합: 카드는 제목 + 우선순위·마감일·태그 배지, 생성은 컬럼 하단 인라인 입력(제목만), 편집은 카드 클릭 시 상세 모달, 검색·필터는 상단 바, 정렬은 컬럼 헤더 메뉴 | Trello 참조 방침과 일관. 인라인 생성은 제목만 필수인 도메인 규칙과 잘 맞고, 정렬이 컬럼 단위라 컬럼 헤더 메뉴가 자연스러움 |
| D-57 | 필터가 적용된 동안 정렬 메뉴를 비활성화한다. 정렬 API는 컬럼 전체 대상 그대로 | 정렬은 덮어쓰기이며 undo가 없어, 보이지 않는 카드의 순서까지 바뀌는 것을 막는다. API 계약이 커지는 "보이는 카드만 정렬"은 채택하지 않음 |
| D-58 | FSD 연결: `shared/api`가 `api-client`로 클라이언트 인스턴스·baseUrl·오류 `code` 변환을 맡고, 티켓 쿼리·뮤테이션 훅은 `entities/ticket`에 둠. 훅 코드 생성은 채택하지 않음 | 공통 설정을 한곳에 모으는 FSD 표준 위치. 이미 정한 TanStack Query + openapi-fetch 조합을 유지 |
| D-59 | 로컬 PostgreSQL은 Docker Compose로 실행 (직접 설치 미채택) | 버전 고정과 `docker compose up` 재현성. Testcontainers로 이미 Docker가 필수라 추가 부담이 없음 |
| D-60 | Node 버전은 `.nvmrc` + `engines`(+ pnpm `engine-strict`)로 고정. 정확한 버전은 구현 시점의 LTS | 가장 흔한 방식이며 `setup-node`가 `.nvmrc`를 읽어 CI 연결이 단순함. Volta는 도구 종속이라 미채택 |
| D-61 | 린트·포맷은 ESLint + Prettier. FSD 경계 검사는 ESLint 플러그인으로 함 (Biome 미채택) | 가장 표준이며 Nest·Next 템플릿과 맞음. FSD 경계 검사 플러그인 생태계는 ESLint에 있어 Biome으로는 학습 목표를 채우기 어려움 |
| D-62 | 커밋 메시지는 Conventional Commits 관례로 쓰되 도구로 강제하지 않음. 브랜치·PR은 기존 `main`/`development` 방식 유지 | 실무 관례를 익히면서 commitlint·husky 설정 비용은 피함. 학습 목표와 거리가 먼 도구 유지비를 줄임 |
